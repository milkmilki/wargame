2026-10-11，基线 `4e454e5`，接续 [预测输入按粮池准备 v17](FORECAST_INPUT_POOLS_V17.md)。本轮保持资源、宗藩和军事规则不变，针对月结尖峰。

## 证据与修改

先核查宣战前的人力门禁：诊断PID26364在第210天宽筛出的31个国家中，没有人力不足者。因此没有调整检查顺序，也不声称它能省掉本样本的资源报告。

随后用只读计时子类诊断PID22400：月结日调用人力容量219次，合计31.845ms；粮食容量40次、5.102ms。计时包含包装和嵌套查询开销，不能把它与粮池成员查询耗时相加。

原月度人力入库和库存截断分别逐国查询容量，每次扫描全图城市。现在 `GameState.base_resource_capacities()` 先遍历城市一次，按原始城市所有者汇总非码头的非负基础人口和粮食产出，再按既有成员查询生成国家容量表。人力容量仍属于本国与和平藩属子树，粮食容量仍按实际共享粮池计算；财政代理、内战断开和循环保护继续使用既有查询。

月度入库改用 `add_manpower_batch()`，按原国家顺序接受人力，返回各国实际入库量。单国 `add_manpower()` 的参数、返回值与上限规则保留，两者共用实际写入函数。`clamp_resource_capacities()` 使用另一份刚生成的容量表，保留仓库扣除及最后一次派生状态刷新顺序。

容量表只在一次同步调用中使用，不跨日、不存入世界状态，也不复用入库时的表去处理后面的库存截断。直接编辑城市产出或所有者而不递增版本号，也会得到新结果。沿用原接口仅排除码头的口径，没有顺便修改交通节点或政治失活节点的产出规则。未修改模板、渲染或补给规则。
