# 月度首都税基批处理 v14

2026-10-11。针对月度结算尖峰。验证有效后单独提交，不推送。

## 改动

实际城市税收结算调用逐城金钱公式，每个首都都再次扫描全部陆地治所，汇总本国基础金钱收入。新 `CityOutputRules.capital_tax_bases` 在同一次月结里只枚举一次陆地治所，按实际财政归属汇总，随后按原城市顺序结算。

与原标量公式相同：基础税基只计行政产出有效的陆地治所、取非负基础金钱，不先乘战乱或藩属治理倍率；资本附加、战乱减产、治理倍率、取整和贡赋顺序保留。纯交通点、码头和行政断联子辖区不贡献税基。查表使用城市的原始归属国编号，入账仍使用财政代理国，避免把继承代理首都误当作财政母国首都。使用64位整数，不把大额自定义预算截断为32位。

`Simulation.city_gold_output` 新增默认兼容的末尾税基参数，普通调用仍自行计算；对照开关 `monthly_capital_tax_batch_disabled=true` 恢复原逐首都扫描。每次月结即时汇总，没有新增跨月缓存，不改变首都距离、行政、军事或贸易规则。

## 另外发现的行政距离问题

诊断显示全体国家首都跳数查询约3.7ms，不是当前最大卡点。但在第180天冻结状态中，发现96条同国相邻治所路线：沿途道路容量为正、每段控制辖区均属该国，旧首都查询仍不认为末端可达。例：国家0、首都0、治所181，物理路径 `[0,558,181]`；交通点558无政治归属，原 `RebellionSystem.capital_hops` 因要求每个物理节点都归本国而跳过它。

这涉及新地图行政距离和虚拟守军费用的正确性，不能用本轮状态一致证明其正确。本轮没有通过删减连通或改变此规则获得性能收益；诊断脚本、样本及源码位置保留，后续独立修复并重新建立相应模拟基线。
