# 日结算优化：行军热循环与紧凑道路缓存

2026-10-10，接续 [补给缓存失效范围](DAILY_COMPUTE_V3.md)。本轮不改变AI节奏或军事模型。

## 修改与依据

完整第240天战争状态中，241～243天每天有130～181个全局到达事件。
约1750支军队反复参与检查，`_is_travelling()`每天调用45.6万～61.5万次。
大量检查发生在军队还没抵达端点的时候。

- 治所到达和岔口检测先判断端点及进度，再执行行军身份判断。谓词没有副作用，
  没抵达端点的军队不需要这些后续检查；实际接触、增援及到达顺序保持不变。
- 当前有向道路缓存使用日内槽位和紧凑整数／浮点数组。军队到槽位的字典只在候选刷新时查询，
  事件热循环直接读取槽位；同一条路的道路键也复用。道路键保持64位，不能截断`lo << 32 | hi`。
- 改换道路、掉头后重新取值；世界或道路版本变化清空槽位并重建候选；让帧后重新查询军队名单。
  缓存只活在一次日推进内，不进入地图模板，也不改变模拟图或军事距离。

仅端点过滤的插桩样本中，行军身份检查降为15.3万～20.6万次，减少约三分之二。
插桩有额外调用和计时开销，这一比例不能直接当作总耗时降幅。

## 回归与尚未解决的问题

新增非到达军队跳过岔口谓词的测试，修改前明确失败，修改后通过。
验证128交通节点、错峰队列、对向遭遇、岔口野战、实际攻城、让帧时新下令，
以及道路版本变化后未换边军队正确刷新时长。专项1841项断言通过。
最终12项回归通过，包括项目编译、同步／分帧、领土事务、双方灭国及35天军事烟测。

战争密集状态另外通过运行期`advance_one_day()`分帧推进241～243天，结果与同步逐日哈希一致。
这组无渲染器的诊断仍观察到143～250毫秒的最大帧间隔：
总计算下降后，AI战役规划的大块同步工作仍会阻塞主线程，不能称运行体验已全部修复。
这不是GUI帧率测量，数据仅定位待处理阶段。
[分帧诊断](evidence/daily_compute_v5/frozen-runtime-spans.json)及
[战役细分计时](evidence/daily_compute_v5/campaign-subprofile.json)表明，准备批次约50～53毫秒，
组件规划在第242天约176毫秒；路径缓存命中并不是唯一剩余成本。
后续继续处理战役规划的重复计算及帧预算，不能以日均下降替代峰值验收。

30年审计仍是加载v6源码的独立进程；本轮没有重启它。
其已越过旧1160天触发点、未发现新的硬错误，但尚未完成10800天；
不能把该进程称为本轮新源码的完整长跑证据。
